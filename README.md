# bipartite-matching-go

一个**本地运行、零外部依赖**的二分图带权匹配服务。输入是两组顶点（左/右）
与一组带权边，支持边的动态增删与改权、带约束的确定性匹配求解、版本化
快照读取、并发更新与查询，以及基于预写日志（WAL）的崩溃恢复。

所有状态只保存在本地目录；HTTP 服务默认仅监听 `127.0.0.1`。

## 构建与运行

```sh
go build ./...
go test ./...                 # 单元 + 对拍 + 并发 + 恢复测试
go run ./cmd/matchingd -addr 127.0.0.1:8080 -data ./data
```

## 匹配语义（三种求解范围）

| 模式 | 主目标 | 未匹配顶点 |
| --- | --- | --- |
| `perfect` 完美匹配 | 在“每个顶点恰好匹配一次”可行的前提下最大化总权重；不可行时失败 | 无 |
| `max_cardinality` 最大基数 | 先最大化匹配对数，再在该基数下最大化总权重 | 允许 |
| `max_weight` 最大权 | 只最大化总权重（负权边不会被选中），基数任意 | 允许 |

顶点集合由**当前仍存在的边**隐式确定：当某顶点最后一条关联边被删除后，
该顶点不再属于图，因此完美匹配的可行性也会随之改变。

### 确定性与平局消解

同一输入（图版本、模式、约束）必然得到字节级一致的结果。在主目标
（基数与总权重）相同的多个最优解中，采用稳定的字典序消解规则：

> 按边键 `(U,V)` 字典序，逐条尝试“强制包含”该边；若包含后仍能达到同一
> 最优基数与总权重则保留，否则永久排除。

等价于选择“按字典序列出的匹配边序列”最小的那个最优解。结果中
`matched`、`unmatched_left`、`unmatched_right` 均按字典序输出，已匹配
与未匹配顶点明确区分。

## 约束

约束通过查询参数传入，求解时直接作用于最小费用流网络（禁止边不建弧，
容量上界作用于源/汇弧），**绝不事后裁剪、绝不静默放宽**：

- `forbidden`：禁止出现的 `(u,v)` 配对。
- `max_left` / `max_right`：每个顶点的配对数上限，缺省为 `1`。

当约束使求解不可行时，返回 HTTP `422` 与可区分的 `reason`，且**不返回
任何未满足约束的部分结果**：

- `perfect_match_infeasible`：当前图与约束下不存在满足全部约束的完美匹配；
- `invalid_constraint`：约束本身非法（如配对上限 `<= 0`、空端点）；
- `invalid_graph`：图数据非法（空端点、权重溢出 int64 费用范围等）。

在 `perfect` 模式下“每个顶点恰好一次”优先于配对数上限，因此完美匹配中
每个顶点仍只出现一次。

## 动态更新与增量求解

- 一次 `update` 是一个**事务**：其中的批量插入/改权（`upsert`）与删除
  （`delete`）要么整体生效，要么完全不生效。
- 提交顺序为“先在内存构造新版本不可变图 → WAL 记录写入并 `fsync` →
  发布版本指针”。未 `fsync` 的更新不会被任何查询观察到。
- 图状态在版本间只做按变更规模的增量复制，单条边变更不会重建整张图。
- 求解侧对固定 `(模式, 约束)` 维护跨版本**残量网络热启动**：新增顶点
  只追加固定节点号，新增边是局部加弧，删除当前未承载流量的边是逻辑
  摘除。热启动结果会用一次冷启动解做**主目标（基数、总权）对拍校验**，
  仅当残量局部优化在复杂交错下未达最优时才以冷启动解为准——正确性
  永远优先，任何提交版本的结果都与从头全量重算一致（由
  `incremental_test.go` 数百步随机增删改冷/热对拍保证）。
- 相同 `(版本, 模式, 约束)` 的重复查询命中结果缓存，为 O(1)，不会重复
  求解。单条边提交（含 WAL `fsync`）在 400 边图上约 4.8ms，且只复制
  O(变更规模) 状态，成本不随图规模退化为全量重建（见 `go test -bench .`）。

## 版本化快照

每次提交产生一个单调递增的整数版本。查询可用 `version` 指定历史版本
（`0` 或省略表示最新）。每个 `Graph`/`Snapshot` 构造后不可变，可被任意
多的并发读共享；查询拿到的永远是**某个完整版本**的边与对应结果，不会
跨版本拼接。

## 持久化与崩溃恢复

- 所有已提交变更先写入目录下的 `wal.log`，帧格式为
  `magic | length | payload | crc32`，并在提交点 `fsync`。
- 启动时按顺序重放 WAL，重建全部版本历史。
- 崩溃时最后一帧若未写完整（截断）或 CRC 校验失败（撕裂），会被物理
  截断丢弃；因此**未完成的更新不会留下部分生效的状态**，已提交的更新
  与匹配结果保持一致。重放截断后可继续正常追加。

## 并发模型

- 更新在存储层写锁内串行提交，多个更新严格等价于某一串行顺序，不丢失
  已提交更新，版本号连续。
- 查询只取不可变快照与读锁，不被进行中的更新长时间阻塞；任何交错下都
  读不到中间状态。
- 热启动求解器按 `(模式, 约束)` 键各自加锁复用；结果带深拷贝缓存，
  调用方修改返回值不会污染服务状态。

## HTTP API

仅监听本地回环，JSON 交互。

### `POST /update`

```json
{
  "upsert": [{"u": "a", "v": "x", "weight": 5}],
  "delete": [{"u": "b", "v": "y"}]
}
```

响应：`{"version": 3}`。

### `POST /query`

```json
{
  "version": 0,
  "mode": "max_weight",
  "forbidden": [{"u": "a", "v": "y"}],
  "max_left":  {"a": 2},
  "max_right": {"x": 1}
}
```

`mode` 取 `max_weight`（默认）、`max_cardinality`、`perfect`。响应：

```json
{
  "version": 3,
  "mode": "max_weight",
  "matched": [{"u": "a", "v": "x", "weight": 5}],
  "unmatched_left": ["b"],
  "unmatched_right": ["y"],
  "cardinality": 1,
  "total_weight": 5
}
```

不可行时：`422 {"error": "...", "reason": "perfect_match_infeasible"}`。

### `GET /version`、`GET /health`

返回当前最新版本号与健康状态。

## 代码结构

- `graph.go`：不可变版本图、顶点/边访问、事务变更应用。
- `solver.go`：最小费用流（下界可行流 + 负环消解 + 逐次最短路）与
  确定性字典序平局消解。
- `incremental.go`：跨版本残量网络热启动求解器。
- `wal.go`：带 CRC 的只追加预写日志与撕裂尾截断恢复。
- `store.go`：版本化存储、WAL 提交、快照历史、二进制记录编解码。
- `service.go`：串行更新、快照查询、约束指纹与结果缓存。
- `server.go` / `cmd/matchingd`：本地 HTTP 接口与可执行入口。

测试：求解器对拍（`solver_exhaustive_test.go`，随机小图枚举全解）、
增量/全量一致性、并发读写（`-race`）、WAL 撕裂恢复、服务重启恢复、
HTTP 端到端与确定性场景。
